# 赛事规则与团队执行口径

> 信息核对日期：2026-08-02。本文是团队执行摘要，不替代官方公告。

## 1. 赛事基本信息

- 赛事：MiniCPM & 昇腾推理优化与应用创新挑战赛
- 核心模型：MiniCPM-o 4.5
- 统一环境：华为昇腾 NPU
- 报名截止：公开赛程显示为 2026-08-14
- 提交截止：公开赛程显示为 2026-08-17
- 复现评审：公开赛程显示为 2026-08-31
- 结果发布：公开赛程显示为 2026-09-04

公开页面曾同时出现“7 月 22 日提交开启”和“7 月 27 日 12:00 提交开启”两种表述。团队不依赖该历史时间点；最终提交以平台当前状态和官方群通知为准。

## 2. 赛道一：高性能推理优化

### 目标

在指定昇腾环境中完成 MiniCPM-o 4.5 推理适配和效率优化，同时保持模型效果、稳定性和可复现性。

### 公开评分重点

- 模型推理适配
- TTFT / 首响速度
- 单 chunk latency
- E2E latency
- 吞吐与并发 session
- 资源利用率和长时间稳定性
- 精度或效果保持
- 部署与复现质量

公开口径是“先校验效果与正确性，再进行性能评测，最后审查复现与工程质量”。正式公式、权重和阈值以官方 starter kit 为准，不在代码里写死猜测权重。

### 必须准备的提交材料

- 可复现代码与配置
- Benchmark 脚本
- 性能报告
- 部署和复现说明

鼓励准备量化模型说明、部署镜像、监控记录和优化分析，但是否提交大型产物必须遵守平台格式和容量限制。

### 上游协作要求

vLLM-Omni 官方 RFC 建议基于上游代码进行小而聚焦的修改，PR 应说明硬件、镜像、CANN/驱动、vLLM Ascend、模型版本、验证命令和前后指标，并避免破坏 CUDA/GPU 行为。

## 3. 赛道二：创新应用

### 目标

基于 MiniCPM-o 4.5 的全模态能力，构建一个可运行、可展示、可体验，并能在指定昇腾环境复现的应用。

### 鼓励方向

- 实时问答和伴随式助手
- 视觉、语音和文本自然交互
- 端侧或低延迟应用
- 多模态场景理解
- 教育、办公、创作和生活服务

### 公开评审维度

- 应用完整度：是否形成完整用户流程和核心闭环
- 交互体验：视觉、语音、文本交互是否自然，延迟是否可接受
- 模型能力展示：是否充分体现 MiniCPM-o 4.5 的全模态能力
- 场景价值：是否解决明确用户问题并具备真实潜力
- 工程质量：Demo、代码结构和部署说明是否可靠
- 演示质量：视频、PPT 和答辩能否讲清作品价值
- 复现可行性：主办方能否根据材料运行或体验核心功能

### 必须准备的提交材料

- 可运行 Demo、Web Demo 或 App
- PPT
- 项目说明
- 演示视频

鼓励补充开源仓库、交互设计说明和应用案例文章。

## 4. 两个赛道共同要求

- 在官方指定的统一昇腾环境中完成复现验证。
- 保留环境版本、启动命令、配置、权重来源、服务入口和验证步骤。
- 提交内容必须与报名赛道匹配，材料缺失或无法复现可能导致成绩无效。
- 文件名优先使用字母、数字、下划线和中划线。
- 不在仓库提交账号令牌、HiDevLab 凭据、模型权重、个人数据或受限数据。

## 5. 尚未确认的规则

公开页面没有明确回答以下问题，必须在官方群或通过 `contact@openbmb.cn` 获得书面确认：

1. 同一参赛者或团队能否同时报名两个赛道。
2. 两个赛道是否允许分别获奖。
3. 两个提交是否允许位于同一私有 GitHub 仓库。
4. 两个项目能否使用相同模型权重、基础镜像或公开上游组件。
5. 最终评测硬件、镜像标签、CANN 版本、评分公式和提交包容量限制。

建议询问原文：

> 请问同一参赛者或团队是否可以同时报名赛道一和赛道二并分别提交作品？两个作品位于同一私有 GitHub 仓库但代码、依赖和提交包完全独立是否允许？是否允许分别获奖？

## 6. 团队执行原则

- 未确认规则不得写成“官方要求”，必须标注“待确认”。
- 官方新公告与本文冲突时，以官方新公告为准，并在同一个 PR 中更新本文和相关提交清单。
- 比赛指标必须记录原始环境和命令；没有证据的数据不得进入最终报告。
- 演示功能必须有稳定降级路径，避免单个实验性能力导致整个作品无法复现。
